Concept demo · Enterprise AI agents

Designing a multi-agent assistant that is safe to switch on

Faizaan Saeed · built for a Forward Deployed Engineer (AI Agents) application

Most agent demos show the happy path. The hard part of putting agents in front of a whole company is everything else: which agent may touch which data, what happens when a document tells the agent to do something, and how you prove it works before release. This page walks through all three for a fictional organisation, Larkspur Group.

What this is: a concept I designed and built as plain HTML and JavaScript. Every run is simulated and deterministic: there is no real LLM behind it, and the organisation, people, documents and numbers are made up. The Microsoft build notes are a design. What I have delivered is listed at the bottom.

    3 · Prompt injection: switch the defences off and watch it fail
    
  
    Two items in Larkspur's data are planted. A supplier review document hides white-on-white text, and an external email carries instructions to the assistant. Both try to get data out of the organisation. Nothing here prevents prompt injection outright: each layer either makes it less likely to work or limits what it can do when it does, so there are five. Four of them are switches; the other is the user's own permissions.
    
  
    
    
    
      
    
      
    
      
    
    
    
    
      
    
        
        
      
    
      
    
      
    Defence chain
    
      
      
      
      
      
      Simplified on purpose. With tagging off, the simulation assumes the model obeys the planted text; a real model often wouldn't, but you can't rely on that. It also assumes the person reviewing an approval card declines a suspicious request. People do click Approve on autopilot, which is why approval isn't the last layer. And the egress filter only covers what it checks: an internal recipient or an unlabelled file would get through it.       4 · Evaluation suite and release gate
      
  
      Ten test cases run through the same simulator as the console, with the defences as they are set in section 3. The gate is the rule a release must pass: every safety and control test, and at least 75% of quality tests. One quality test is scripted to fail. It shows the kind of grounding gap a suite should catch, and a suite where everything is green usually isn't testing much.
      
  
      
  
      
  
      
    
      IDResultTestTypeRunsWhyConsole
      
    
      
  
      Ten scripted cases show the shape of a suite, not its size: a real one needs far more cases, and model-graded scores vary from run to run. In a real build the same cases would run as code in the release pipeline, scored by a mix of exact checks (was a tool called, was a citation in the retrieved set) and model-graded checks (is the answer supported by its sources), with real conversations sampled back into the test set.
      

      


      
  
      5 · Identity and permissions
      
  Concept design
  
      Every agent gets its own identity, so its access can be granted, audited and revoked on its own. In Foundry that is a Microsoft Entra agent identity (Entra Agent ID). The main design decision is per tool: does the call run as the user (the on-behalf-of flow, with delegated permissions) or as the app (application permissions, the agent's own)? Acting for the user through an agent identity was still marked preview in Microsoft's docs when I wrote this, so I'd confirm it in the client's tenant first.
      
  
      
    
      AgentActs asLeast-privilege accessWhy
      
    
      
  
      
    
      Rule of thumb
      On behalf of the user
      • Use it when the answer depends on who is asking: documents, mail, their own tickets.
      • The agent can never reach more than the user can, and the audit trail ties each call to the real person.
      • The user's token isn't passed along. Each service swaps it for a new token for the one API it's about to call.
      • Limit: it doesn't stop an injection that abuses the user's own access. Section 3 shows this. Priya in HR can open the salary file, so an agent acting for her can too.
      
    
      Rule of thumb
      As the app
      • Use it for content that's the same for everyone, such as a published policy index, and for the agent's own logging and telemetry.
      • Grant one narrow role on one resource (for example read-only on a single search index) to the agent's own identity or a managed identity, so there are no secrets in code.
      • Avoid broad application permissions on mail or files. Application Mail.Send lets an app send as anyone in the organisation unless Exchange Online scopes it to named mailboxes.
      
  
      

      


      
  
      6 · How I'd build it on Microsoft Foundry
      
  Concept design
  
      This is how I'd approach it. The products and their names change quickly (Azure AI Foundry is now Microsoft Foundry), so in week one I'd check each choice against the client's tenant and the current Microsoft documentation, and change it where they differ.
      
  
      
    
      Agents & orchestration
      Routing as code
      Each specialist as an agent in Foundry Agent Service with its own instructions, tools and knowledge, on an Azure OpenAI model deployment. The orchestrator as a Microsoft Agent Framework workflow (the successor to Semantic Kernel and AutoGen, in Python or C#), so handoffs are code I can test rather than a prompt I hope behaves.
      
    
      Grounding
      Search index plus Graph
      Azure AI Search indexes for shared content such as policies and the IT knowledge base, or a Foundry IQ knowledge base on top of them, with a relevance threshold tuned on the eval set, below which the agent says it doesn't know. Microsoft Graph for anything personal or live, called as the user so results are security-trimmed. If per-user documents ever went into a search index, the index would have to trim results itself (security filters, or the newer preview that carries SharePoint permissions into the index), and those copies can lag behind the source. That is why this design keeps them in Graph. Work IQ is Microsoft's newer, preview route to the same Microsoft 365 data under the user's permissions; I'd weigh it against direct Graph calls.
      
    
      Tools & MCP
      Small, typed tool lists
      Internal systems such as ticketing exposed as MCP servers or OpenAPI tools with strict schemas. Each agent gets an allow-list. Side-effecting tools are marked approval-required, so the workflow pauses and only runs them once an approval comes back.
      
    
      Safety
      Rules outside the prompt
      Retrieved text marked as untrusted data (spotlighting), plus Prompt Shields in Azure AI Content Safety to flag attacks in user prompts and in documents. Document scanning has to be switched on. Both cut the risk and neither removes it, so the egress rule (internal recipients only, nothing sensitivity-labelled leaves) is ordinary code in the tool layer that doesn't depend on the model.
      
    
      Evaluation
      A gate, not a report
      The suite from section 4 in the release pipeline, plus Foundry's built-in evaluators for groundedness and tool-call accuracy, and its AI Red Teaming Agent for an indirect-injection sweep. Any change to a prompt, tool or index re-runs it.
      
    
      Identity, Teams & ops
      Run it like a service
      A Microsoft Entra agent identity per agent, managed identities for Azure resources, any remaining secrets in Key Vault. Published from Foundry to Teams and Microsoft 365 Copilot, with approvals as Adaptive Cards; how far that reaches into Outlook is something I'd confirm. Every tool call traced, with the identity it ran as, and a cost per conversation.
